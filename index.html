ARCHITEKTURA

Dokument i silnik tłumaczeniowy są rozdzielone

Format dokumentu określa ścieżkę wejścia. Formaty nietekstowe korzystają z Filter Engine, natomiast TXT, Markdown i przyszłe formaty tekstowe omijają filtry i trafiają do backendu jako tekst.

DOCX · ODT · HTML/XHTML · EPUB · XLIFF→Filter Engine
dekodowanie / ekstrakcja→wybrany backend→Filter Engine
rekonstrukcja→dokument
TXT · MD · przyszłe formaty tekstowe→tekst→wybrany backend→tekst wynikowy
01

Ekstrakcja i rekonstrukcja

Filter Engine dekoduje formaty nietekstowe, pracuje na jednostkach tłumaczeniowych i odtwarza dokument po zakończeniu tłumaczenia.

02

Bezpośrednia ścieżka tekstowa

TXT, Markdown oraz przyszłe formaty tekstowe nie przechodzą przez filtry dokumentowe. Backend otrzymuje tekst bezpośrednio.

03

Cache i anulowanie

SQLite cache uwzględnia tekst, prompt, skill, model i temperaturę, ma 7-dniowy TTL i może zostać wyczyszczony z GUI.

FORMATY

Dwie ścieżki obsługi plików

Filter Engine dotyczy formatów, których struktura musi zostać rozkodowana przed tłumaczeniem. Format tekstowy jest traktowany jako tekst wejściowy i omija filtry. Ta zasada obejmuje również przyszłe formaty tekstowe dodawane do aplikacji.

DOCX.docx · Filter Engine
ODT.odt · Filter Engine
HTML / XHTML.html · .htm · .xhtml · Filter Engine
EPUB.epub · Filter Engine
XLIFF 2.0.xlf · .xliff · Filter Engine
TXT / Markdown.txt · .md · bez filtrów

TRANSLATEGEMMA

Specjalny kontrakt w llama.cpp, nie osobny backend

TranslateGemma działa w V4 jako wartość chat_template="translategemma" dla llama.cpp. W tym trybie Lingua wykrywa język źródłowy, a aplikacja buduje dedykowane żądanie. Historyczne ścieżki FastAPI/OpenVINO nie są aktywną częścią V4.

Ważne: repozytorium nie zawiera wag modelu TranslateGemma. Model podlega własnym warunkom Google.
