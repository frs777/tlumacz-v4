# PLAN-2026-10-05 — architektura i kolejność doprowadzenia Tłumacza V4 do używalności
## 1. Cel
Doprowadzić Tłumacz V4 od aktualnego stanu Release Candidate / NIEGOTOWY DO FINAL RELEASE do stanu używalnego i możliwego do powtarzalnego wydania.
Segment jest wydzielany tylko wtedy, gdy ma własną odpowiedzialność, kontrakt, cykl życia, testy i granicę integracyjną. Nie dzielimy kodu według plików na siłę.

Docelowy model pozostaje modularnym monolitem:
```text
QML / GUI
    ↓
Application / Composition Root
    ↓
wspólne kontrakty + registry
    ↓
┌──────────────┬──────────────┬──────────────┐
│ Filter Engine│ Backendy     │ Infrastructure│
│              │ llama/cloud/ │ cache/secrets│
│              │ apertium     │ runtime      │
└──────┬───────┴──────┬───────┴──────────────┘
       ↓              ↓
Document Units → TranslationOrchestrator → Result/Filter validation
       ↓
wynik dokumentowy
```

Nie tworzymy mikroserwisów tylko dlatego, że istnieją osobne funkcje.

## 3. Kolejność realizacji
### Etap A — używalność techniczna
**0 → 1 → 2 → 3 → 4**. Najpierw wiarygodność artefaktu i procesu dokumentowego, następnie kontrakt filtrów, potem llama.cpp/TranslateGemma jako pierwszy lokalny backend, a dopiero następnie pełna rekonstrukcja Apertium. Nie traktować braku eng-pol jako pojedynczej poprawki; audyt wskazuje problem całego runtime/data/package.

**Exit A:** jednoznaczny source; aktywne filtry mają kontrakt; Apertium discovery > 0; deklarowane pary mają smoke; brak ścieżek V3; runtime działa po relokacji.

### Etap B — backendy sieciowe i infrastruktura
**5 → 6 → 7**. Mozhi pozostaje providerem Cloud. Custom jest niezależnym adapterem OpenAI-compatible dla lokalnych i zdalnych serwerów. Sekrety lokalne/Custom/Cloud są przechowywane w pliku .key w katalogu konfiguracyjnym użytkownika.

**Exit B:** llama.cpp i Cloud przechodzą kontrakty; TranslateGemma ma realne E2E; sekrety nie trafiają do settings JSON; shutdown zamyka cache i runtime.

### Etap C — GUI
**7** dopiero po ustaleniu kontraktów. GUI nie może utrwalać funkcji, których pipeline nie obsługuje.

### Etap D — dystrybucja
**8 → 9**: source → wheel → install → runtime. Packaging jest osobnym produktem technicznym.

### Etap E — finalizacja
**10 → final gate**. Dokumentacja i repozytorium opisują stan po zmianach; dopiero wtedy finalny audit.

## 4. Granice modułów
### Rdzeń
DocumentTranslationService, DocumentProcessor, TranslationOrchestrator, ChunkPlanner, PromptBuilder, TranslationExecutor, ResultValidator, CancellationToken i kontrakty domenowe. Rdzeń nie importuje Qt ani konkretnego providera.

### Filter Engine
FilterRegistry, FilterSession, FilterHost, filtry formatowe, inline-code/marker lifecycle i round-trip validation. Filter nie zna Cloud, llama.cpp ani Apertium.

### Backendy
Każdy backend ma osobną granicę kodu:
```text
backends/
  llama_cpp/
  cloud/                  # providerzy Cloud, w tym Mozhi
    providers/
  custom/                 # OpenAI-compatible: lokalny i zdalny serwer
  apertium/
```
Custom nie jest podmodułem Mozhi/Cloud. Może współdzielić kontrakt transportowy z Cloud i abstrakcje kompatybilne z llama.cpp, ale posiada własny adapter, konfigurację endpointu, health/capabilities i lifecycle.

### GUI
QML i bridge prezentują stan oraz akcje. Nie przejmują logiki tłumaczenia, transportu, retry, discovery ani rekonstrukcji dokumentu.

## 5. Wspólny kontrakt backendów
Każdy backend musi posiadać: capabilities, supported language pairs, translate units, health, cancellation, close/lifecycle i jawne klasy błędów.
Backend otrzymuje jednostki tłumaczeniowe, nie dokument ani skeleton. Nie zmienia kolejności, inline codes, struktury dokumentu ani UI i nie wykonuje niejawnego fallbacku.

## 6. Plan scalenia i kompatybilności
### Document → Filter
DocumentProcessor → FilterRegistry → FilterSession → TranslationUnit[]. Jednostka musi zachować stabilne ID, kolejność, source/target, inline codes, języki, translatability i metadata.

### Filter → Orchestrator
TranslationUnit[] → TranslationOrchestrator → TranslationResult[]. Orchestrator zachowuje ID i kolejność oraz nie zna formatu dokumentu.

### Orchestrator → Backend
TranslationRequest → BackendRegistry → konkretny backend → BackendResult. Wynik musi być zgodny ze wspólnym ResultValidator.

### Backend → Filter
BackendResult → ResultValidator → MarkerValidator → Filter.merge/write. Backend nigdy nie zapisuje dokumentu.

### GUI → Application
QML ↔ QmlApplicationBridge → TranslationApp → wspólne kontrakty. Bridge jest adapterem prezentacyjnym. Dekompozycję bridge wykonujemy po characterization tests.

### Packaging → wszystkie moduły
Manifest release obejmuje Python package, QML, SVG, Markdown help, Filter Host, Apertium runtime/data, wymagane biblioteki i metadata/licencje.

## 7. Macierz kompatybilności
| Para | Wymaganie |
|---|---|
| GUI ↔ Application | stabilne properties/actions, kompletne i18n |
| Application ↔ Core | brak Qt w core |
| Core ↔ Filter Engine | TranslationUnit contract |
| Core ↔ Backend | wspólny port |
| llama ↔ TranslateGemma | chat template + ISO source/target |
| Cloud ↔ Mozhi | provider contract |
| Cloud ↔ Custom | wspólne kontrakty transportowe, ale osobny moduł i konfiguracja endpointu |
| Apertium ↔ Core | jednostki tekstowe, bez logiki dokumentowej |
| Filter ↔ Filter Host | wersjonowany JSONL + workspace |
| Runtime ↔ Packaging | relokowalne ścieżki |
| Packaging ↔ CI | clean install + smoke |
| Docs ↔ Code | aktualny status i evidence |

## 8. Strategia testowania
Każdy segment: characterization test → regresja błędu → test kontraktu → integracja → release smoke, jeżeli dotyczy artefaktu.
Nie nazywać kontrolowanego fake runtime'u E2E.

Release gate: pytest, Ruff, mypy, compileall, qmllint, build wheel, wheel content, clean install, CLI smoke, QML smoke, runtime smoke, checksum i manifest.

## 9. Kryterium używalności
Program jest technicznie używalny, gdy użytkownik uruchamia V4 bez pomylenia z V3; co najmniej jeden lokalny backend działa stabilnie; Cloud działa; aktywne formaty wykonują extract → translate → write; wynik zachowuje strukturę i inline codes; Apertium nie deklaruje niedziałających par; sekrety są izolowane; shutdown jest czysty; aktualny wheel instaluje się poprawnie.

Final release ma dodatkowo wymagania platformowe, dependency/licensing i CI zgodnie z deklarowanym zakresem.

## 2026-10-06 — aktualizacja realizacji segmentu 7: Security/Lifecycle

Segment 7 został rozpoczęty i przeszedł pierwszą implementację TDD:
- migracja legacy sekretów do SecretStore jest wykonywana centralnie przed ładowaniem ustawień GUI;
- zapis profilu ustawień przez bridge nie utrwala sekretów;
- shutdown cache/runtime jest centralizowany w `TranslationApp.close()`;
- ownership mismatch llama.cpp nie może zostać „zgubiony” przez wyzerowanie referencji runtime;
- `aboutToQuit` pozostaje punktem wejścia do centralnego shutdown.

**Status:** gate weryfikowany 2026-10-07; kanoniczna konfiguracja GUI to `$HOME/.config/tlumacz/config.json`. Do formalnego zamknięcia pozostaje świeża pełna walidacja suite oraz końcowa kontrola ResourceWarning/orphan processes.
