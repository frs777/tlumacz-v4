PLAN WDROŻENIA — MODULARNE BACKENDY I ROZSZERZALNY WŁASNY SERWER
Data: 2026-10-07

Status: PLAN DO AKCEPTACJI / BEZ ZMIAN W KODZIE

1. CEL

Doprowadzić warstwę backendów do stanu, w którym:
- istniejące backendy pozostają funkcjonalnie niezmienione;
- „Własny serwer” pozostaje opcją podłączenia zewnętrznego serwera OpenAI-compatible;
- dodanie kolejnego backendu nie wymaga modyfikowania wspólnego pipeline'u tłumaczenia;
- backendy są rejestrowane przez wspólny kontrakt i registry, a nie przez rosnący zestaw instrukcji if backend == ...;
- konfiguracja, capabilities, health i lifecycle są deklarowane przez moduł backendu;
- wariant „custom” nie jest mylony z providerem Cloud, mimo współdzielenia transportu/abstrakcji.

2. STAN WYJŚCIOWY — USTALENIA Z AUDYTU

Aktualnie istnieją osobne moduły:
- src/tlumacz/backends/llama_cpp/
- src/tlumacz/backends/cloud/
- src/tlumacz/backends/apertium/

Istnieje wspólny kontrakt TranslationBackend z translate() i health_check().

Istnieje BackendRegistry, ale nadal zawiera routing zależny od konkretnych nazw:
- llama
- cloud/custom
- apertium

BackendRegistry posiada również konkretne pola implementacji, m.in. cloud, apertium i _llama.

„custom” jest obecnie aktywną opcją GUI i korzysta z CloudRouter. Jest to już funkcjonalny mechanizm podłączenia zewnętrznego serwera OpenAI-compatible, ale architektonicznie jest jeszcze specjalnym przypadkiem routingu Cloud.

Istnieją testy custom:
- tests/test_backend_registry_custom.py
- testy GUI, ustawień i persystencji związane z custom.

Wcześniejszy plan architektoniczny definiuje Custom jako osobny segment odpowiedzialności: adapter OpenAI-compatible dla lokalnych i zdalnych serwerów, z własną konfiguracją endpointu, health/capabilities i lifecycle.

3. ZASADA DOCELOWA

Docelowy model:

BackendContract
    ↓
BackendRegistry
    ↓
identyfikacja backendu + capabilities
    ↓
konkretny moduł backendu
    ↓
wspólny BackendResult

Dodanie backendu powinno docelowo wymagać:
1. utworzenia modułu backendu;
2. implementacji wspólnego kontraktu;
3. deklaracji capabilities/configuration;
4. rejestracji modułu;
5. testów kontraktowych.

Nie powinno wymagać zmian w:
- DocumentProcessor;
- Filter Engine;
- ChunkPlanner;
- TranslationOrchestrator;
- TranslationExecutor;
- ResultValidator;
- writerach;
- wspólnym kontrakcie dokumentowym.

5. ETAP 1 — USTABILIZOWANIE WSPÓLNEGO KONTRAKTU

Rozszerzyć TranslationBackend do pełnego kontraktu backendowego, jeżeli analiza potwierdzi brakujące elementy:
- identyfikator;
- nazwa wyświetlana;
- capabilities;
- supported language pairs / sposób deklarowania możliwości;
- translate;
- opcjonalny batch;
- health_check;
- cancellation;
- lifecycle/close;
- jawna klasyfikacja błędów.

Nie wymuszać sztucznie tych samych mechanizmów na backendach, które mają różne lifecycle. Kontrakt ma opisywać capability, a nie implementację.

6. ETAP 2 — WPROWADZENIE REJESTRACJI BACKENDÓW

Przebudować BackendRegistry z rejestru warunkowego na registry instancji/definicji backendów.

Zamiast:
- if backend == "llama"
- if backend == "apertium"
- if backend in {"cloud", "custom"}

docelowo:
- registry.get("llama");
- registry.get("cloud");
- registry.get("custom");
- registry.get("apertium").

Routing ma zależeć od zarejestrowanego backendu i jego capabilities.

BackendRegistry nie powinien znać szczegółów implementacji każdego backendu poza composition root.

7. ETAP 3 — ODDZIELENIE CUSTOM OD CLOUD NA POZIOMIE ODPOWIEDZIALNOŚCI

Nie tworzyć drugiego transportu HTTP tylko dla custom.

Zachować możliwość współdzielenia:
- transportu OpenAI-compatible;
- normalizacji odpowiedzi;
- błędów transportowych;
- timeoutów.

Jednocześnie custom powinien mieć własny moduł odpowiedzialności:
src/tlumacz/backends/custom/

Moduł powinien obsługiwać:
- endpoint użytkownika;
- konfigurację;
- API key, jeśli wymagany;
- model/engine;
- health;
- capabilities;
- lifecycle po stronie aplikacji, jeśli występuje.

Custom nadal oznacza „użytkownik dostarcza serwer”; Tłumacz nie powinien automatycznie uruchamiać zewnętrznego serwera.

8. ETAP 4 — CAPABILITIES

Wprowadzić deklaratywny opis możliwości, np.:
- translate;
- batch;
- health;
- cancellation;
- streaming, jeżeli kiedyś będzie potrzebny;
- source/target language support;
- OpenAI-compatible API.

Pipeline pyta backend o capability zamiast zakładać, że konkretny backend ją posiada.

Przykład:
Jeżeli backend nie ma natywnego batcha, TranslationExecutor może użyć bezpiecznej ścieżki jednostkowej zgodnej z kontraktem.

Nie dodawać specjalnego if-a dla każdej przyszłej implementacji.

9. ETAP 5 — KONFIGURACJA

Rozdzielić:
- wspólny BackendRequest;
- konfigurację specyficzną dla backendu;
- dane sekretne;
- capabilities.

Nie rozszerzać centralnego BackendRequest dziesiątkami pól tylko dlatego, że jeden backend ich potrzebuje.

Docelowo konfiguracja powinna być przekazywana do backendu jako jego własny, typowany profil/kontrakt.

10. ETAP 6 — GUI

GUI nie może znać szczegółów implementacyjnych backendu.

Backend selector powinien korzystać z listy zarejestrowanych backendów.

Dla custom zachować:
- nazwę „Własny”;
- pole endpointu;
- informacje o kontrakcie OpenAI-compatible;
- niezależną wartość custom_server_url.

Własny serwer nie może nadpisywać konfiguracji llama.cpp.

Przyszły backend może dostarczyć własne capabilities/config UI bez modyfikowania logiki wspólnego pipeline'u.

11. ETAP 7 — TEST KONTRAKTOWY „NOWY BACKEND”

Dodać sztuczny backend testowy, np. TestBackend, implementujący tylko wspólny kontrakt.

Test ma wykazać:
- rejestracja działa;
- selection działa;
- translate działa;
- health działa;
- pipeline tłumaczy dokument;
- Filter Engine pozostaje bez zmian;
- ChunkPlanner pozostaje bez zmian;
- TranslationOrchestrator pozostaje bez zmian;
- TranslationExecutor pozostaje bez zmian.

To jest najważniejszy test rozszerzalności.

15. ETAP 11 — EXIT GATE

Wdrożenie można zamknąć, gdy:

1. każdy aktywny backend implementuje wspólny kontrakt;
2. registry nie wymaga rozbudowy warunków if backend == ... dla nowych backendów;
3. custom pozostaje osobną opcją podłączenia własnego serwera;
4. custom nie jest traktowany jako provider Cloud;
5. transport OpenAI-compatible może być współdzielony;
6. konfiguracja backendu jest rozszerzalna;
7. capabilities są deklaratywne;
8. nowy TestBackend przechodzi przez cały pipeline bez zmian w pipeline;
9. istniejące backendy przechodzą regresję;
10. GUI custom zachowuje dotychczasowe zachowanie;
11. sekrety nie trafiają do zwykłej konfiguracji;
12. dokumentacja jest zsynchronizowana;
13. pełna walidacja projektu jest wykonana.
